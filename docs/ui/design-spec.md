## 1. 三条设计前提

在动手之前，先确认三个判断。它们决定了后面所有取舍。

### 1.1 中央区放地质剖面，不放全息光球

你给的三张参考图中央都是一个发光环/球。它好看，但**不承载任何信息**——运维盯着它看不出井下发生了什么。

换成地质剖面后，中央区同时是**导航**：五个 MVA 测点在剖面上有真实的空间位置（近地表、浅部、井筒、深部），超阈值时读者能立刻知道"是哪一层出了问题"。这是归因的起点。

光球的视觉冲击力用另一种方式保留：注入点的高亮核心 + 羽流的径向辉光 + 极细的等压虚线环。它仍然"像科幻界面"，但每一个像素都在描述物理状态。

### 1.2 六种状态，不是五种

`ops/contracts.py` 里 `SEVERITIES` 是五级（normal / notice / warn / alert / critical），但还有第六态 `INDETERMINATE`（不可判定：无读数、读数不可信、阈值未配置）。

界面上它必须与"正常"在视觉上拉开距离，否则看板会变绿——而那是唯一不会报错的失败。用了三重信号叠加：

| 信号 | 正常 | 不可判定 |
|---|---|---|
| 颜色 | 青绿 | 中性灰 |
| 边框 | 实线 | **虚线** |
| 数值 | 数字 | **破折号 —** |
| 措辞 | 正常 | 不可判定 |

三重冗余是有意的：缩略列表里颜色可能失真，破折号在小字号下可能被忽略，但三者同时误导的概率很低。

### 1.3 品牌色不进数据层

中石化红 `#D8232A` 与本项目的 critical `#B23A3A` 色相只差 4°，明度接近。如果品牌色用在数据元素上，操作员会把"品牌"读成"严重告警"。

所以品牌色被严格限制在**身份与框架**四处：页眉细线、Logo、客户联合品牌位、面板角标。数据区永远是青/钢蓝 + 六级语义色。

原型里点右上三个色点可以看到：换肤后数据区完全不变。

## 2. 视觉规范

### 2.1 色彩令牌

```css
/* 底色：深海蓝三层，最深的一层仍不是纯黑 */
--bg-0: #070F16;   /* 页面 */
--bg-1: #0B1A24;   /* 面板 */
--bg-2: #102532;   /* 抬升元素 */
--bg-3: #16303E;   /* 卡片 */

/* 描边：全部带透明度的青，避免生硬的纯色线 */
--line:   rgba(122,178,204,.14);
--line-2: rgba(122,178,204,.30);

/* 文字三级 */
--txt-0: #E8F1F6;  /* 数值与标题 */
--txt-1: #9DB4C4;  /* 说明 */
--txt-2: #64798A;  /* 次要信息、单位 */

/* 强调：低饱和青 + 钢蓝 */
--acc:   #58B8C9;
--acc-2: #7E9CB8;

/* 六级语义色 —— 与品牌色隔离 */
--sev-normal:   #3F8F84;
--sev-notice:   #B99A3E;
--sev-warn:     #D08442;
--sev-alert:    #C25A45;
--sev-critical: #B23A3A;
--sev-unknown:  #6E7C88;
```

**为什么不是纯黑**：`#000` 在 OLED 屏上会让相邻的青色出现光晕（halation），长时间注视后残影明显。`#070F16` 保留了"深海"的纵深感，同时让青光有依托。

**为什么青色要低饱和**：`#00E5FF` 那种高饱和青在暗底上会产生色差边缘（chromatic aberration），且与告警红形成互补色冲突，视觉上互相抢注意力。`#58B8C9` 的饱和度约 50%，能读但不刺。

### 2.2 字体

```css
--font-cjk: "Microsoft YaHei UI", "PingFang SC", "Noto Sans SC", sans-serif;
--font-num: "Bahnschrift", "DIN Alternate", "Roboto Condensed", "Arial Narrow", sans-serif;
--font-mono: "Consolas", "JetBrains Mono", "SF Mono", monospace;
```

**关于 DIN**：你的要求里点名了 DIN。但 DIN / DIN Next 是 Monotype 的商业字体，**每台终端都要授权**，私有化交付时这笔钱躲不掉。

替代方案是 **Bahnschrift**——Windows 10 起系统自带，是 DIN 1451 的变体，字重可变，且**免授权**。在 Windows 工控机上渲染效果与 DIN 几乎无差。如果客户是 macOS/iPad 环境，回退到 DIN Alternate（macOS 自带）或 Roboto Condensed（Apache-2.0）。

数值统一加 `font-variant-numeric: tabular-nums`——等宽数字让同列数值小数点对齐，这在扫读一列压力值时是刚需。

### 2.3 尺寸与节奏

| 项 | 值 | 理由 |
|---|---|---|
| 圆角 | 2–3 px | 工业界面用直角，圆角只用于柔化，不做胶囊 |
| 面板间距 | 10 px | 紧凑但不粘连 |
| 面板内边距 | 12 px | |
| 字号阶 | 10.5 / 11.5 / 13 / 15 / 17 / 25 / 30 px | 工程师模式整体 ×1.15 |
| 行高 | 1.45（正文）/ 1.15（大数字） | 数字行高收紧避免视觉断裂 |

### 2.4 HUD 装饰的克制边界

参考图里的扫描线、网格、角标，在本方案里只保留两处：

1. **极淡网格底**（`rgba(88,184,201,.030)`，64 px）——只在页面背景，不叠加到面板上。
2. **面板对角角标**（12 px 的 L 形线）——标记面板边界，替代粗边框。

**全部去掉的**：扫描线动画、噪点纹理、发光描边、故障闪烁、粒子背景。这些在演示视频里加分，在连续 8 小时的班次里是视觉噪音。

## 3. 布局

### 3.1 三栏结构

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏 54px  Logo │ 客户位 │ 链条状态四段 │ 新鲜度 │ 时钟 │ 换肤 │ 模式 │
├────────────┬──────────────────────────────┬──────────────────┤
│ 左 320px   │ 中 flex                      │ 右 352px         │
│            │                              │                  │
│ 关键指标   │ 地质剖面 + CO₂ 运移           │ AI 助手对话       │
│ 2×2 卡片   │ （指挥舱）                    │                  │
│            │ 或 16 测点全量表（工程师）      │                  │
│ 告警列表   │                              │ 待确认操作        │
│ 5 条+盲区  │ 语音控制台 118px              │ （常驻，非弹窗）   │
├────────────┴──────────────────────────────┴──────────────────┤
│ 状态栏 30px  冲突 │ 阻断 │ 盲区 │ 无读数 │ 报告状态 │ 阈值来源  │
└──────────────────────────────────────────────────────────────┘
```

**为什么左窄右宽**：左侧是"扫描"任务（快速判断有没有事），窄栏减少眼球水平移动距离；右侧是"阅读"任务（对话与确认），需要宽度承载文字。

**为什么待确认操作常驻而不是弹窗**：弹窗会被关掉，关掉之后"有一件事等你决定"这个事实就消失了。常驻卡片让它在处理完之前一直可见。

### 3.2 断点

| 宽度 | 左 | 中 | 右 |
|---|---|---|---|
| ≥1500 px | 320 | flex | 352 |
| 1200–1500 px | 288 | flex | 316 |
| <1200 px | 折叠为抽屉 | flex | 折叠为底部面板 |

大屏汇报（≥2560 px）时不拉伸，改为 `max-width: 2200px` 居中——无限拉伸会让字距失衡。

## 4. 双模切换的实现

不是"做个开关"，而是三件事同时发生。原型里点右上「指挥舱 / 工程师」可以直接看到。

| 变化 | 指挥舱 | 工程师 |
|---|---|---|
| 中央区 | 地质剖面 + 粒子动效 | **16 测点全量表** |
| 粒子 / 旋转环 / 波形 | 开 | **全部 `display:none`** |
| 字号 | 13 px 基准 | **15 px 基准** |
| 左侧顺序 | 指标卡在上 | **告警在上**，指标卡隐藏 |
| 语音控制台 | 显示 | **隐藏**（现场噪声下不可用，留着是死控件） |
| 底色 | 深海蓝渐变 | **纯色 `#0C1014`**，去渐变去网格 |

```css
html[data-mode="engineer"] *{animation:none !important;transition:none !important}
html[data-mode="engineer"] .fx{display:none !important}
```

**关键实现约束：`.fx` 只能标装饰，不能标数据。**

羽流本身是数据（它表示 CO₂ 扩散范围），所以羽流的两个椭圆**不加 `.fx`**，在工程师模式下仍然显示；只有粒子、旋转环、虚线等压环加 `.fx`。如果图省事把整个 `<g>` 都标成 `.fx`，工程师模式会得到一个空剖面——把数据当装饰删掉了。

**关于强光环境**：深色底在户外阳光下会变成镜子。如果客户现场有强光场景，工程师模式应该再提供一个浅色变体（`#F2F4F6` 底 + `#0B1A24` 字）。本版未做，因为多数 CCUS 中控室是室内可调光环境。

## 5. 关键组件的设计依据

每一个组件都对应 `ops/` 的真实字段。这不是"照着字段画图"，是"字段决定了必须这样画"。

### 5.1 告警卡

```
┌─────────────────────────────────────┐
│ [严重] 环空压力            12.4 bar │  ← severity / label / value
│ 井筒 · 阈值 12.0 · 09:20            │  ← stage / threshold_value / ts
├─ 展开后 ────────────────────────────┤
│ 判据  超 critical 阈值 12.0 bar      │  ← rationale[0..n] 逐条
│       连续 3 点在 alert 以上         │
│       1h 内 +1.8 bar                 │
│ 出处  项目设计文件 §4.3              │  ← provenance
│ 归因  井筒完整性疑似劣化（strong）    │  ← attribution.confidence
│ 已排除 ~~温度效应~~                  │  ← ruled_out（删除线，仍可见）
│ 处置  降注入速率至 35 t/h（注入班）   │  ← actions[].action / .owner
└─────────────────────────────────────┘
```

三个刻意的设计：

- **`rationale` 逐条列出，不折叠成一句"超阈值"**。运维要问的是"为什么是这一级"，而不是"严重度是多少"。三条规则命中就写三行。
- **`ruled_out` 的条目用删除线保留，不隐藏**。读者需要看到"我们考虑过这个原因、因为某条读数排除了它"，否则会怀疑是不是漏了。这是 `ops/contracts.py` 里 `Attribution` 注释的原话，界面上必须落实。
- **`provenance` 放在展开区第一屏**，不用 tooltip。现场工程师戴手套、环境嘈杂，悬浮提示根本点不到。

### 5.2 指标卡

带**阈值余量**而不是只显示数值：

```
捕集率
92.4 %
阈值 90.0 · 余量 2.4
```

"92.4%" 单独看无法判断好坏，"余量 2.4" 才能。方向由 `SensorSpec.direction` 决定：`high`（越高越坏）显示"余量 = 阈值 − 当前值"，`low`（越低越坏）反之。

超阈值时卡片边框转 warn 色，余量文字变红并写"超 warn 阈值 0.05"。

### 5.3 引用角标

AI 回答里每个数字后面跟一个可点的角标：

```
A1 井环空压力 12.4 bar [alarm:A-…-annulus_p]
```

角标内容就是 `Citation.render()` 的输出（`[kind:ref]`），点击跳到对应告警卡。这是"每个数字可回代"在界面上的落点——**如果读者无法一键回到原始读数，可回代就只是文档里的承诺**。

知识库面板里已经落地了另一类角标：检索结果上的 `[n]`，点击跳到该文献的对应切片（见 5.6）。两类角标共用同一条原则，但编号的作用域不同——`[alarm:…]` 是稳定的告警 ID，`[n]` 只是本次检索的序号。

### 5.4 语音控制台

状态只有四个：**待机 / 聆听 / 思考 / 回复**。没有第五个"开心"或"警觉"。

环形动效只在"聆听"和"思考"时加快旋转速度，其余时间保持慢速——动效是状态指示器，不是装饰。原型里点中央圆环可以循环切换四种状态。

**语音的权限边界**：

| 语音可以做 | 语音不可以做 |
|---|---|
| 查询工况、打开某个测点 | 直接开关阀门 |
| 请求生成报告草稿 | 直接调泵速 |
| 发起"建议降速"的讨论 | 任何改变物理状态的操作 |

语音在工业现场的错误率远高于办公环境（压缩机 85 dB、安全帽、方言、术语混淆——"井口压力"会被识别成"进口压力"）。所以语音最多做到"打开确认面板"，落笔必须是人手点击 + 签名。

### 5.5 高危操作确认

常驻在右栏底部，点击「确认执行」弹出二次确认，弹窗里必须包含三样东西：

1. **动作的具体参数**（42 t/h → 35 t/h），不是"降速"这种模糊描述；
2. **系统已核验 / 未核验的边界**（"环空超阈值已确认，但盖层完整性未确认"）；
3. **操作人签名输入框**（必填，空值提交按钮不放行）。

第 2 条是最容易漏的：只写"确认执行吗"等于把责任推给人；写明"系统知道什么、不知道什么"才是把决策权交还给人。

### 5.6 知识库面板

放在**右栏**（与对话并列的两个 Tab），不放中央。中央区是空间索引，回答"这件事发生在哪一层"；知识库回答"这条结论出自哪篇论文"，它天然是对话的支撑面——引用角标点开之后落在这里，读者不必把视线从结论上移开半个屏幕。放进中央等于用 55% 的面积显示一个文字列表。

**这个面板要回答的不是"库里有多少篇"，是"这个知识库能信到什么程度"。** 所以首屏必须有三件事：

| 要显示的 | 不显示会怎样 |
|---|---|
| **缺口**：盘上 24 篇、图谱里 22 篇，差的 2 篇点名列出 | "共 22 篇"读起来是完整的，而它其实漏了 2 篇 |
| **可引用性**：只有图谱切片带 `file_path` 血缘 | 用户以为向量分支的结论也能点回原文 |
| **三种检索状态**：`ok` / `empty` / `unavailable` | 把"没跑起来"读成"库里没有"，然后去补文献 |

#### 引用角标的语义

`reference_id` 是 **LightRAG 在一次响应内**给来源编的号（"1"、"2"…），排序依据是该文件在本次结果里出现的次数。它**不是**全局文档 ID：

- 同一个 `[3]` 在两次查询里指向不同文献；
- 同一篇文献在两次查询里的编号也不同。

所以界面上的 `[n]` 只能解释为"本次检索的第 n 个来源"，不能存下来当书签。要长期指向一篇文献，只能用 `file_path`——那是入库时写入的血缘，稳定。这条必须写在界面上（角标的 `title`），因为它是唯一一处"看起来像 ID 但又不是"的字段。

#### 两种检索后端，只有一种能给出处

| 后端 | 存什么 | 血缘 |
|---|---|---|
| LightRAG（图谱） | 实体 / 关系 / 原文切片 | ✅ 切片带 `file_path` |
| Chroma（向量） | 原文切片 | ❌ metadata 只有 `{"source": "legacy_v2"}` |

这不是待办，是当前的事实。所以界面上向量库那一栏固定显示"无文件级血缘：向量分支的召回无法回溯到具体文献"。把它藏起来的结果，是用户对一条无法溯源的结论产生与可溯源结论同等的信任。

#### 为什么内部还要分两页

右栏只有 320 px。概览（数字 + 缺口 + 24 行文档清单）和检索（输入 + 证据卡）叠在一页会有三屏高，而**滚动条一出现，缺口那段就看不见了**——恰好把最该被看见的东西推出了视口。

#### 一个被知识库暴露出来的布局缺陷

右栏接上知识库之后，检索结果能有三屏高，而 `main` 的 grid 隐式行是 `auto`：行高被内容撑到 3000 px，中央剖面（`h-full`）跟着变成 3000 px 高，相机按 3000×900 取景，于是**整个剖面被压到画布最底下**，看起来像"3D 挂了"。

修法是 `grid-rows-[minmax(0,1fr)]`：`1fr` 单独用会被 `min-height:auto` 顶开，仍然按内容算高度。窄屏是单列三行，行高钉死后必须让 `main` 自己可滚，否则下面的面板会被裁掉且滚不到。

| 地质剖面 | `echarts-gl` 的 `surface` 系列做层位曲面；粒子层用 `@react-three/fiber` 叠在上面 |
| 管网拓扑 | `xyflow`（React Flow）自定义 edge 做流光 |

### 6.3 必须从零写

| 元素 | 为什么没有现成的 |
|---|---|
| 六级状态色带 + 不可判定视觉 | 没有任何通用库知道"不可判定"要和"正常"分开 |
| 归因候选卡（含已排除折叠区） | `Attribution` 结构是本项目特有的 |
| 引用角标与跳转 | `Citation.render()` 格式是本项目特有的 |
| 审批状态机（draft→submitted→approved/rejected→reopened） | `ops/reports.py` 的 `TRANSITIONS` 是业务逻辑，不是 UI 组件 |
| 双模切换 | 没有库会预设"关掉动效同时换成表格" |
| 语音意图 → 动作的权限闸门 | 安全逻辑，必须自己写 |
| 盲区提示条 | 同上 |

**一句话总结**：外壳和控件 80% 能复用，业务语义 0% 能复用。而后者才是产品壁垒。

## 7. 中央 3D 场景的实现

中央区是 `web/src/three/geoscene.ts`（一个纯 three.js 场景，不依赖 React）+ 
`web/src/components/GeoSectionCanvas.tsx`（React 包装层，负责生命周期、标签叠加、
WebGL 探测）。

### 7.1 为什么不用 `@react-three/fiber`

这个场景只有一个画布、一台固定机位的相机、没有拾取交互、不需要每帧把状态同步回
React。r3f 的价值在于"把场景变成可组合的 React 树"，而这里恰好没有需要组合的东西 ——
引入 reconciler 换来的只是一个要额外解释的抽象层和更大的包。

判断标准是**有没有第二个场景**。如果将来要加管网拓扑视图、且两个视图共享材质与相机，
再迁到 r3f 是合理的；现在迁是提前抽象。

### 7.2 场景图：三种图元，三种身份

| 图元 | 身份 | 指挥舱 | 工程师 | 实现 |
|---|---|---|---|---|
| 地层板 | 背景（层位参照） | 有 | 有 | `BoxGeometry` + 程序化 canvas 纹理 + `EdgesGeometry` |
| 羽流**剖面轮廓** | **数据**（CO₂ 波及范围） | 有 | 有 | `ShapeGeometry`（由 `plumeRadiusM` 采样出的多边形） |
| 羽流**体**（3D 包络） | 装饰（让人看出它是个体） | 有 | **无** | 参数曲面 + `AdditiveBlending` |
| 粒子 | 装饰（流动感） | 有 | **无** | `Points` + 自定义 `ShaderMaterial` |
| 等压虚线环 | **数据**（压力影响范围 > CO₂ 范围） | 有 | 有 | `LineDashedMaterial` + `computeLineDistances()` |
| 测点球 | **数据**（六级色 + 空心/实心） | 有 | 有 | `SphereGeometry`，颜色取自 CSS 变量 |

工程师模式关掉的是"体"和"粒子"，**不是羽流本身**。第一版把整个羽流当特效删掉，
结果工程师模式得到一个空剖面 —— 而"CO₂ 到底铺到哪一层、离监测井还有多远"
正是现场最需要看的东西。

### 7.3 正交相机，不是透视

剖面的深度尺必须**线性**。透视投影下 0–300 m 会比 900–1200 m 占更多像素，
于是同一张图上两段等长的深度画出来不一样长 —— 而深度尺的全部意义就是"可以按比例读"。

立体感由三样东西承担，不需要透视来凑：切块的厚度（160 m）、侧壁与顶面、
地表网格。俯角 9°、偏航 3°，`OrthographicCamera` 的 `left/right/top/bottom`
由 `frameCamera()` 按画布长宽比反解。

### 7.4 羽流：参数曲面，形状本身是物理

羽流不是球、不是水滴、也不是圆锥。CO₂ 比地层水轻，注入后受浮力**向上**运移，
到盖层底界停住，然后沿盖层底面**横向铺开** —— 一根供给柱顶着一个贴着盖层的饼。

```ts
// web/src/lib/section.ts —— 3D 与 SVG 降级版共用这一份
export function plumeRadiusM(p: PlumeGeometry, t: number): number {
  const feeder = 150;                       // 供给柱半径（m）
  const s = Math.min(1, Math.max(0, t));
  const flare = Math.pow(s * s * (3 - 2 * s), 1.4);   // 上段张开更快
  const bulb = 24 * Math.exp(-Math.pow(t / 0.1, 2));  // 射孔段的局部扩散
  return feeder + (p.radius - feeder) * flare + bulb;
}
```

三个参数各自修过一次，每次都是因为**形状在暗示一个不存在的构造**：

1. `smoothstep(0.5, 1, t)` + 供给柱 70 m → 从半高开始线性张开，画出来是高脚杯。
   高脚杯意味着"从某一深度起突然出现水平通道"，图上并没有这条通道。
2. 供给柱 90 m、张开压到顶部 20% → 一条水平肩线 + 一根针，还是高脚杯。
   90 : 380 = 1 : 4.2，而真实羽流的底部也有可观宽度。
3. 现在：张开铺满整个高度，顶部直接取满半径（**CO₂ 在盖层下是平的，不是圆顶**），
   再在顶缘 4% 的高度里收 10% 半径，去掉"杯口"那条硬边。

### 7.5 粒子：位移上限必须小于局部半径

```glsl
// 顶点着色器（节选）
vec3 p = position;
float s = aSeed * 6.2831853;
float amp = 0.045;                          // 位移上限（场景单位）
p.x += sin(uTime * 0.55 + s) * amp;
p.z += cos(uTime * 0.42 + s * 1.3) * amp * 0.6;
p.y += sin(uTime * 0.85 + s * 1.7) * amp * 0.55;

vec4 mv = modelViewMatrix * vec4(p, 1.0);
gl_Position = projectionMatrix * mv;
gl_PointSize = aSize * uSize * uSizeScale * uPixelRatio;

vAlpha = 0.30 + 0.70 * (0.5 + 0.5 * sin(uTime * 1.1 + s * 2.3));
vAlpha *= 1.0 - 0.62 * vTint * vTint;       // 边缘饱和度低
```

- 粒子只在原地做小幅环绕（±4.5 m），**不能自由飘**。让它飘看起来更"流体"，
  但那样图上显示的羽流范围就变成了粒子群的包围盒 —— 一个由随机数决定的值，
  而不是模型给的范围。在一个用来判断"CO₂ 有没有到监测井"的界面上，这不能接受。
- 径向衰减 `1 - 0.62·tint²`：不做衰减时粒子会一直堆到轮廓线上，整条羽流像一袋沙子。
- 叠加混合下**密度直接等于亮度**：3000 个点、5 m 直径、片元 alpha ×0.62，
  是试出来的平衡点。5200 个点时轴心会叠成一片实心白。

### 7.6 标签在 DOM 里，不在 WebGL 里

中文字形图集要几 MB，而这块屏上只出现 15 个标签。做法是：

1. 场景给每个锚点一个世界坐标（`anchors: Map<string, Vector3>`）；
2. 每帧渲染后回调 `onAfterRender`，把锚点用 `Vector3.project()` 投到画布像素；
3. React 直接改对应 DOM 节点的 `style.transform`（**不走 setState**，否则每帧一次重渲染）。

这样标签复用系统字体、能选中、能跟随 `prefers-reduced-motion`，代价只是每帧 15 次
样式写入。

### 7.7 分包

`three` 压缩后约 130 KB gzip。用动态 `import()` 拆成独立 chunk：左栏的告警卡是
"这个班次要不要叫人"的全部依据，它不该等一个 3D 库下载完才出现。

CI 有一道守卫盯着这件事（`.github/workflows/ci.yml` 的 `3D scene is still code-split`）：
断言 `dist/assets/geoscene-*.js` 存在、且首屏 chunk < 320 KB。有人把它改成静态
`import` 时，"左栏先亮"这个性质会静默消失 —— 没有报错，只是工控机上多等一秒。

### 7.8 降级：WebGL 起不来的时候

老工控机的 Intel 集显驱动、远程桌面会话、被策略禁用的硬件加速 —— 这三样在现场都不
罕见。`lib/webgl.ts` 探测失败时切到 `GeoSectionFallback`（SVG 版），
它和 3D 版**共用 `section.ts` 的全部坐标与羽流函数**，所以两个版本不可能画出两个
不同的剖面。差异只在表现力：没有厚度、没有粒子、没有透视。

### 7.9 实现期踩到的三个坑

1. **同一条 `opacity` 属性，在"有 map"和"没有 map"两条路径上语义不同。**
   材质没挂 `map` 时最终 alpha 就等于 `opacity`（0.82）；挂了 `map` 时是
   `opacity × 底纹自身的 alpha`（0.26）。差 4 倍 —— 覆盖层比盖层还亮，
   而盖层是这张图上最该被看见的一层。修法是所有层都挂同一张底纹，alpha 语义统一。
2. **正交相机下粒子尺寸不能除以视深。** 沿用透视的 `/-mv.z`，在 120 单位的相机
   距离下把 5 m 的粒子算成 0.1 px。粒子其实一直没被看见，看到的只是叠加出来的雾。
3. **GLSL 注释里的反引号会提前闭合模板字符串。** 写 `/-mv.z` 时那对反引号把
   TS 的模板字面量截断了，`tsc` 报的是"找不到 mv"，指向的是另一行。构建不报错。

> **three.js 为主 + SVG 为降级**：echarts-gl 的 `surface` 系列画不出"盖层下贴顶铺开"

### 9.1 第 1 周：骨架与真实数据

- 三栏（左报警 / 中主视觉 / 右对话占位）+ 底栏六态计数。
- 左栏接的是**真实响应**：`web/src/fixtures/*.json` 由
  `scripts/capture_ops_fixtures.py` 用 `TestClient` 从 `/api/ops/alarms` 抓取，
  CI 跑 `--check` 比对，接口一变就红。场景是构造的，**阈值一个数字都没改**。
- 右栏先落**语音权限边界**：它不依赖任何后端，且是这套界面里唯一"做错了会伤到人"的部分。

实现期发现的两个语义错误（都已修）：

1. `alarm.threshold_value` 是"命中了哪一级的线"，`normal` 时是 `null`。
   拿它当"测点的阈值"用，所有正常测点都显示成「无阈值」，与真正的盲区无法区分 ——
   而盲区是这套界面最需要说清的东西。正确来源是测点目录里的 `warn`。
2. 越限后仍以 `warn` 为基准显示「阈值 20.0 · 超 critical 1.6」，一句话里两个数
   互相矛盾。基准线必须跟着越过的等级走：`严重线 40.0 · 超 1.6`。

### 9.2 第 2 周：地质剖面

- `web/src/lib/section.ts` 是几何的**唯一真值**：层序、测点深度与横向位置、
  羽流半径函数。3D 与 SVG 两个渲染器都从它取数。
- 5 个 MVA 测点在剖面上有真实深度与横向位置，超阈值时能直接归因到层位。
- 中央区两个 Tab：「剖面」与「全链」。同一份数据的两种读法，
  并排会让人以为它们各说各的，而 1440 宽下并排会把每栏都挤到不能读。
- 羽流几何目前是**示意值**，界面上照原样标注「示意（未接储层模拟）」——
  它来自储层模拟，不是从压力读数反推的。用 `reservoir_p` 去"推算"羽流半径，
  得到的是一个看起来很像真数的编造值，而它会被截图放进汇报材料。

### 9.3 第 2.5 周：知识库

语料（`ccus_docs/` 24 篇）、图谱（`lightrag_storage/`）与向量库（`chroma_petro/`）
本来就在仓库里，`lightrag_retriever.py` 也早就能检索。缺的从来不是数据，
是**接口和界面**——没有任何一条路径能让操作员看见"系统到底知道什么"。

后端拆成 `api_kb.py`（与 `api_ops.py` 同一分工），静态端点零重依赖：

- `GET /api/kb/overview` —— 语料 / 图谱 / 向量库三块状态 + 缺口清单；
- `GET /api/kb/documents` —— 盘上每篇一行，**遍历盘上文件而不是图谱记录**，
  否则没进图谱的那 2 篇根本不会出现在列表里，而列表读起来仍然完整；
- `GET /api/kb/documents/{name}` —— 切片原文，引用角标的落点。
  **不依赖模型**：Ollama 挂了引用跳转照样能用，否则它会在最需要时失效；
- `POST /api/kb/search` —— 唯一需要模型的端点，函数内懒加载。

实现期踩到的三个坑：

1. **`kv_store_full_entities.json` 的键是 `doc-<hash>`，不是实体名。**
   直接取 `len(dict)` 得到的是"22 篇文档"，而它会显示成"22 个实体"。
   实测差 20 倍（22 vs 4,826），且界面上没有任何交叉校验能发现它是错的。
   必须摊平 `entity_names` 再按名字去重。
2. **实体的 `file_path` 是多值的**（`<SEP>` 拼接）。`CO2 Leakage` 这个实体
   来自 16 篇论文，血缘就是 16 个文件名连成的**一个**字符串。
   第一版把它当单个文件名塞进 `source` 字段，界面上显示成一个既不像文件名、
   也不能点开的长条——更糟的是它**看起来像**一个文件名。
   切片没有这个问题（一个 chunk 只属于一篇），所以实体/关系用 `sources: []`，
   切片用 `source: ""`，形状不同是有意的。
3. **`build_fragments` 主动消灭出处。** 它把两端实体的完整描述拼进关系片段，
   产出长文本喂 reranker——那是对的，reranker 只看语义。但拼接之后
   "这句话来自哪篇论文"已无从得知（一个片段混了三个来源）。
   所以证据卡另起一个纯函数模块 `kb_evidence.py`，一条证据一张卡、绝不合并。
   两个模块的不变量是**相反**的，放在一起迟早有人为了少写几行在证据路径上
   复用拼接函数，而结果不会报错——只是每条引用都指向同一篇文献。

**建议先做工程师模式**。它没有 3D 动效、没有语音，但它是客户真正每天用的那个。
指挥舱模式是投标和汇报用的，做起来快、演示效果好，容易让人误以为进度很快。

## 10. 本方案不做什么

- **不做纯光球/流体背景**。中央区的每个像素都要描述物理状态。
- **不做语音直接操作设备**。见 5.4。
- **不做"一切正常"的绿色大屏**。有盲区就写盲区，有不可判定就写不可判定。
- **不做无出处的阈值**。界面上的每条阈值线都必须能展开看到来源（`provenance`）。
- **不引入 AGPL / GPL 依赖**。Grafana 再好也不用，理由见侦察报告 5.4。

## 11. 当前实现的样子

三张图都是**真实运行截图**（`vite preview` + 无头 Edge，1680×1000），不是设计稿。
数据来自 fixture —— 而 fixture 是 `capture_*_fixtures.py` 从真实接口抓的，
所以图上每一个数字都能在后端复现。

**指挥舱 · 知识库概览。** 中央是地质剖面（真实深度、正交相机），右栏是知识库：
24 篇语料 / 22 篇已建图 / 874 切片 / 4,826 实体，以及那 2 篇没进图谱的文件名。
缺口用警示色单独成块，因为它比总数更重要。

左栏顶部是**注入压力上限校核**卡片：井底峰值 336 bar / 破裂压力 452 bar =
74.4 %，上限 90 %（40 CFR §146.68(b)）。它排在告警列表**之前**，因为它是唯一
一项法规直接给定的判据，而告警是项目自己配的线。进度条上那条竖线是上限刻度 ——
没有它，"74.4 %" 无法判断是宽裕还是贴着上限。

![指挥舱](web/deck.png)

**指挥舱 · 检索。** 6 篇来源、12 片原文证据。每条证据带 `[n]` 角标与文件名，
点文件名跳到该文献的对应切片。底部两行统计："全部 12 片可回溯到原文"与
"2 片以公式为主，不宜作为机理证据"—— 为 0 时也要说一句，读者才能确认
这件事被检查过。

那 2 片是**实测的检索缺陷**，不是构造的例子：问「盖层完整性对 CO2 泄漏风险
的影响」，排名第一的是一条 `𝑡+1 = 𝐶(𝑥𝑡)𝑥𝑡+1 + 𝐷(𝑥𝑡)𝑢𝑡` 的离散格式公式。
